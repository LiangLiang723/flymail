# 历史同步正文补全进度设计

## 问题与证据

同步管理页在历史任务进入 `current_page = 2` 后只显示“正在补全正文和附件”，卡片上的数字仍是邮件摘要缓存数。摘要可能已经达到 `2691 / 2691`，但后端仍需逐封从 IMAP 拉取完整正文、附件元数据和内嵌图片，因此页面长时间没有任何数字变化，看起来像任务卡死。

当前生产数据确认任务仍在工作：目标账号的“已归档”文件夹在 20 秒内正文已检查数从 429 增长到 491，任务心跳也持续更新。日志没有异常，根因是进度口径缺失，而不是后台死锁。

## 目标

- 正文补全阶段显示实时、可验证的 `已处理 / 待处理总数`。
- 进度直接来自当前用户账号的本地缓存状态，不依赖仅统计摘要的 `fetched_messages`。
- 不新增数据库列，不迁移或删除 `/Docker/flymail/data` 中的数据。
- 不改变 IMAP 同步顺序、用户隔离、正文缓存语义、暂停/继续/重试接口。

## 方案选择

### 方案 A：给同步任务表新增正文计数列

优点是接口读取简单；缺点是需要表结构迁移，并且任务中断、重启或旧数据恢复时容易出现计数与真实缓存不一致。

### 方案 B：从缓存表实时计算正文检查进度（采用）

根据 `cached_messages` 与 `cached_message_empty_body_checks` 计算：

- `body_total_count`：该文件夹已缓存的邮件摘要数。
- `body_remaining_count`：正文和 HTML 都为空，且尚无“远端确认正文为空”记录的邮件数。
- `body_checked_count = body_total_count - body_remaining_count`。

该口径与正文补全工作循环实际使用的筛选条件一致，容器重启后也能从持久化数据恢复真实进度，无需迁移。

### 方案 C：只把文案改成“任务仍在运行”

实现最小，但仍不能证明任务是否推进，也无法区分慢任务和真正停滞，因此不采用。

## 后端设计

在 `backend/db/__init__.py` 增加 `get_cached_body_check_progress(account_id, folder)`。函数复用现有文件夹别名展开逻辑，使用单条聚合查询返回总数和剩余数，并在 Python 中计算已处理数。

`backend/routes/settings.py::_build_folder_progress` 为每个文件夹附加：

- `body_total_count`
- `body_checked_count`
- `body_remaining_count`

这些字段只描述当前账号、当前文件夹的本地缓存，不访问 IMAP，也不泄露其他用户数据。

## 前端设计

`HistorySync.vue` 在正文补全阶段读取当前文件夹的正文进度，阶段提示显示为：

```text
正在补全正文和附件 · 已归档 · 正文 491 / 2691
```

暂停或等待继续时使用同一计数口径。页面现有三秒轮询会重新读取数据库聚合值，因此数字会随后台逐封处理而变化。摘要进度区域继续保持原有含义，不把正文进度混入摘要计数。

## 错误与边界

- 文件夹尚无缓存时显示 `0 / 0`，但只在正文补全阶段附加计数。
- 若当前文件夹无法在进度列表中匹配，保留原阶段文案，不伪造数字。
- 正文真实为空的邮件在成功比对后由 `cached_message_empty_body_checks` 计为已处理，避免永远显示未完成。
- 本次不并发拉取完整邮件，避免同一 IMAP 连接的并发安全风险。

## 测试与验收

- 数据库单元测试验证剩余数查询与 `已处理 = 总数 - 剩余数`。
- 路由单元测试验证文件夹进度返回三个正文计数字段。
- 前端静态回归测试验证正文阶段显示实时计数。
- 完整执行后端测试、前端测试和生产构建、Shell 与 Compose 检查、Docker 镜像构建和独立临时容器持久化验证。
- 正式替换容器时复用 `/Docker/flymail/data:/data`，不清空或迁移现有邮件数据。
