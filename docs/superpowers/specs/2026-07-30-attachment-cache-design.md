# FlyMail 附件缓存按需下载、容量控制与 SHA-256 去重设计

日期：2026-07-30

## 1. 目标

本设计解决 FlyMail 邮件附件与内嵌图片缓存持续占用磁盘的问题，同时保持邮件正文、内嵌图片和已缓存附件的可用性。

验收目标：

1. 历史同步继续缓存邮件正文和内嵌图片，但不再主动下载普通附件。
2. 普通附件在用户点击下载时按需缓存。
3. 每个用户拥有独立的普通附件缓存容量上限。
4. 默认上限为 2048 MB；`0` 表示不限制；非零值不得小于 100 MB。
5. 超出上限时，按用户维度使用最近最少使用（LRU）规则淘汰普通附件缓存。
6. 普通附件和内嵌图片都使用 SHA-256 内容比对，全局只保留一份物理文件。
7. 只有最后一条数据库引用删除后，才删除共享物理文件。
8. 同一用户对同一 SHA-256 的多个普通附件引用只计一次逻辑配额；不同用户引用同一对象时，各自计入该用户配额。
9. 正文与内嵌图片不计入普通附件容量上限。
10. 用户降低上限后立即执行容量清理，并返回逻辑释放量和实际磁盘释放量。

## 2. 非目标

本次不做以下改动：

- 不压缩或裁剪邮件正文。
- 不改变邮件摘要、正文或附件元数据的用户隔离规则。
- 不删除远端邮箱中的任何邮件或附件。
- 不对邮件备份目录中的 `.eml` 文件做内容去重。
- 不引入外部对象存储、Redis 或新的生产依赖。
- 不把附件容量改成全站共享配额。

## 3. 当前问题

当前附件按邮件目录分别保存：

```text
/data/flymail/files/download/<邮箱>/<年>/<月>/<UID>/<part>_<filename>
```

相同附件在不同邮件、文件夹、账号或用户中会重复保存。历史同步还会主动下载普通附件，因此大附件会快速占用磁盘。

现有附件下载接口已经支持本地文件不存在时从远端重新获取，因此普通附件可以安全改成按需缓存；但需要保留附件元数据，以便页面仍能显示名称、大小和类型。

## 4. 总体方案

采用全局内容寻址对象存储。所有普通附件与内嵌图片按 SHA-256 保存到统一目录：

```text
/data/flymail/files/objects/sha256/<前两位>/<完整 SHA-256>
```

邮件附件记录继续按 `account_id + folder + uid + part_number` 标识业务引用，但不再拥有独立物理文件。多个引用可以指向同一个对象。

对象存储只负责物理内容去重；用户权限仍由现有账号、邮件和 `user_uid` 关系控制。任何下载接口必须先完成现有邮件账号归属校验，不能凭对象哈希直接读取文件。

## 5. 数据模型

### 5.1 `attachment_cache_objects`

新增对象表：

| 字段 | 类型 | 说明 |
|---|---|---|
| `content_sha256` | `CHAR(64)` 主键 | 文件内容 SHA-256，小写十六进制 |
| `size` | `BIGINT` | 物理文件字节数 |
| `local_path` | `LONGTEXT` | 对象文件绝对路径 |
| `created_at` | `DOUBLE` | 首次写入时间 |

对象表不保存手工维护的 `ref_count`。引用数量以 `cached_attachments` 的实际查询结果为准，避免计数漂移导致误删。

### 5.2 `cached_attachments`

在现有表上新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `content_sha256` | `CHAR(64)`，默认空字符串 | 当前引用的共享对象哈希；空值表示未缓存 |
| `last_accessed_at` | `DOUBLE`，默认 0 | 普通附件最近成功访问时间；内嵌图片可记录写入时间但不参与配额淘汰 |

保留现有 `local_path` 字段，用于兼容现有代码和迁移过程。迁移完成后，已缓存记录的 `local_path` 指向共享对象路径；未缓存普通附件的 `local_path` 和 `content_sha256` 为空。

新增索引：

- `idx_cached_attachments_sha256(content_sha256)`
- `idx_cached_attachments_user_inline_access(user_uid, is_inline, last_accessed_at)`

### 5.3 用户设置

复用 `user_settings` 表，新增键：

```text
attachment_cache_limit_mb
```

规则：

- 未设置时返回默认值 `2048`。
- `0` 表示不限制。
- 非零值必须大于等于 `100`。
- 设置按当前 `user_uid` 保存，互不影响。

## 6. 文件写入流程

新增独立的附件对象存储服务，职责包括：

1. 接收下载得到的字节内容或临时文件。
2. 流式计算 SHA-256。
3. 生成对象路径。
4. 以原子方式创建对象文件。
5. 写入或复用对象记录。
6. 更新附件引用。
7. 清理失去全部引用的旧对象。
8. 触发当前用户普通附件配额检查。

写入规则：

1. 内容先写入对象目录下的临时文件，文件名包含随机值。
2. 写入过程中同步计算 SHA-256，避免为大附件复制额外内存。
3. 临时文件完整落盘并校验长度后，生成最终对象路径。
4. 若最终文件已经存在，删除临时文件并复用已有对象。
5. 若最终文件不存在，使用同文件系统内原子重命名写入。
6. 数据库引用更新成功后，才能清理引用原来的旧对象。
7. 发生异常时删除本次临时文件，不删除已有对象。

并发写入相同内容时，允许多个请求同时计算哈希，但最终只保留一个对象文件。数据库使用对象哈希主键保证对象记录幂等。

## 7. 历史同步和增量同步

### 7.1 内嵌图片

内嵌图片继续自动下载，因为邮件 HTML 离线显示依赖这些内容。

下载后：

- 写入共享对象存储。
- `cached_attachments.content_sha256` 和 `local_path` 指向共享对象。
- 邮件 HTML 中的 CID 继续替换为现有受权限保护的附件接口 URL。
- 内嵌图片不计入普通附件容量上限，也不参与 LRU 淘汰。

### 7.2 普通附件

历史同步、增量同步和详情预取只保存附件元数据：

- 文件名
- MIME 类型
- 大小
- part number
- content ID
- 是否内嵌

普通附件不主动写入物理文件，记录中的 `content_sha256` 和 `local_path` 保持为空。

如果同步详情中已经携带普通附件二进制，也不自动持久化，避免历史同步绕过按需缓存策略。

### 7.3 用户点击下载

普通附件下载顺序：

1. 校验当前用户对邮箱账号和邮件的访问权限。
2. 若引用对象存在且物理文件存在，更新 `last_accessed_at` 并返回本地文件。
3. 若数据库引用存在但文件缺失，清空失效引用，再走远端下载。
4. 若账号离线且本地无有效对象，返回当前已有的离线错误。
5. 从远端下载后写入共享对象存储。
6. 更新当前附件引用及 `last_accessed_at`。
7. 执行该用户普通附件配额清理。
8. 返回文件。

## 8. 配额计算

每个用户的普通附件逻辑用量定义为：

> 当前用户所有 `is_inline = 0` 且 `content_sha256` 非空的附件引用中，按 SHA-256 去重后的对象大小之和。

示例：

- 同一用户的 10 封邮件引用同一个 20 MB 文件：该用户逻辑用量计 20 MB。
- 两个用户分别引用同一个 20 MB 文件：两个用户各计 20 MB，磁盘物理占用仍为 20 MB。
- 同一对象同时被普通附件和内嵌图片引用：普通附件用户按规则计入配额，内嵌图片引用本身不计配额。

容量检查只统计数据库仍有效且对象记录存在的引用。发现对象文件缺失时，将其作为无效缓存引用处理，不计入用量。

## 9. LRU 淘汰

当用户普通附件逻辑用量超过非零上限时：

1. 按该用户的普通附件对象分组。
2. 每个 SHA-256 的访问时间取该用户所有普通附件引用中的最大 `last_accessed_at`。
3. 按访问时间从旧到新排序。
4. 每次选中一个 SHA-256，清空该用户对该对象的全部普通附件缓存引用。
5. 重新计算用户逻辑用量，直到不超过上限。
6. 每清空一组引用后检查全局真实引用数；为零时删除对象记录和物理文件。

清空引用只修改：

- `content_sha256 = ''`
- `local_path = ''`
- `last_accessed_at = 0`

附件名称、大小、类型、part number 和邮件记录继续保留，后续仍可重新下载。

### 9.1 降低上限

设置接口保存较低上限后立即执行相同 LRU 清理。接口响应提供：

- 清理前逻辑用量
- 清理后逻辑用量
- 清除的附件引用数
- 清除的用户去重对象数
- 实际删除的共享对象数
- 实际释放的物理字节数

### 9.2 `0` 的行为

`0` 表示不限制，不触发 LRU 淘汰。SHA-256 去重和引用清理仍然生效。

## 10. 引用删除和对象回收

以下操作可能移除附件引用：

- 删除邮箱账号
- 清空账号或文件夹缓存
- 邮件从本地缓存删除
- LRU 淘汰
- 数据迁移替换旧引用

统一使用对象存储服务删除或清空引用。流程为：

1. 在数据库事务中读取待删除引用涉及的 SHA-256 集合。
2. 删除或清空业务引用。
3. 提交数据库事务。
4. 对每个受影响 SHA-256 查询全局剩余引用数。
5. 剩余引用为零时删除对象记录和物理文件。

物理删除失败时保留或恢复对象记录，并记录不含敏感信息的警告，交由后续垃圾回收任务重试。不得因为文件删除失败回滚已经完成的邮件业务删除。

为避免竞态，删除物理对象前需要再次确认数据库无引用；写入方在数据库中建立引用前必须确保对象记录和文件已存在。

## 11. 设置页设计

设置页新增“普通附件缓存”卡片，包含：

- 当前逻辑用量
- 当前物理共享对象总量仅作为说明，不用于用户配额
- 容量上限输入框，单位 MB
- 默认值提示：2048 MB
- `0` 表示不限制的说明
- 正文和内嵌图片不计入上限的说明
- 保存按钮

校验：

- 只允许整数。
- 小于 0 拒绝。
- `1–99` 拒绝并提示“非零容量不能低于 100 MB”。
- 允许 `0` 和大于等于 `100` 的值。

保存成功后刷新当前用量，并显示本次清理结果。清理可能耗时，接口应在后台线程执行文件操作，避免阻塞事件循环；设置页在请求完成前保持保存状态。

## 13. 现有数据迁移

迁移必须保护 `/Docker/flymail/data`，且可以在中断后重跑。

### 13.1 普通附件

现有普通附件本地文件将被移除，数据库保留完整附件元数据，并清空 `content_sha256`、`local_path` 和 `last_accessed_at`。之后用户点击时重新按需下载。

删除前必须确认：

- 数据库记录属于普通附件。
- 文件路径位于 FlyMail 下载目录内。
- 文件不是共享对象目录中的文件。

### 13.2 内嵌图片

现有内嵌图片逐个处理：

1. 检查文件存在且路径位于允许目录。
2. 流式计算 SHA-256。
3. 写入或复用共享对象。
4. 更新引用。
5. 确认数据库更新成功后删除旧独立文件。

重复内嵌图片自动合并为同一对象。

### 13.3 孤立文件

迁移完成后扫描旧下载目录。只有确认没有任何 `cached_attachments.local_path` 引用的文件才可删除。目录为空后可删除空目录，但不得删除下载根目录、对象目录、备份目录或上传目录。

### 13.4 可恢复性

迁移不依赖单独的全局“已完成”标记，而通过每条记录当前状态判断：

- 已有有效 `content_sha256` 且对象存在：跳过。
- 内嵌图片仍指向旧路径：继续迁移。
- 普通附件仍指向旧路径：清空引用并安全删除旧文件。
- 引用为空：已完成或原本未缓存，跳过。

因此容器重启后可以安全重跑。

迁移在应用启动后以受控后台任务执行，不阻塞健康检查。任务需要互斥锁，避免同一容器内重复运行；单容器部署不需要分布式锁。

## 14. 垃圾回收

对象目录可能因崩溃、文件删除失败或数据库提交失败留下孤立对象。新增轻量垃圾回收：

- 应用启动迁移结束后执行一次。
- 后续每周执行一次。
- 只删除数据库无引用的对象记录和对象文件。
- 对象目录中没有对象记录的文件，需超过安全等待期后才删除，避免删除并发写入中的临时或刚创建文件。
- 临时文件超过安全等待期且没有活跃写入时可删除。

本次只需满足单容器运行，不引入跨实例协调。

## 15. 安全和隔离

- 对象路径由服务器根据 SHA-256 生成，不能接受客户端路径。
- 文件读取继续经过现有用户、账号、邮件和附件归属校验。
- 不在日志中输出邮箱密码、OAuth 令牌、数据库连接密码或会话密钥。
- 日志可以输出对象哈希的短前缀、大小、用户 UID 和清理统计，但不输出附件正文。
- 所有旧文件删除必须经过允许目录校验，拒绝符号链接逃逸和目录穿越。
- 共享物理对象不改变数据库中的用户隔离；用户无法枚举或直接访问其他用户对象。

## 16. 错误处理

- 哈希计算或写入失败：不建立缓存引用，返回下载失败；已有对象不受影响。
- 数据库更新失败：删除本次新建且仍无引用的对象文件。
- 对象文件缺失：清空失效引用，在线账号尝试远端重新下载。
- 配额清理失败：附件下载本身可成功返回，但记录警告并安排后续清理；不得删除刚下载文件后仍返回不存在路径。
- 用户调低容量后的清理失败：设置值仍保存，接口返回明确错误或部分清理统计，后台任务继续重试。
- 远端附件不可用：保持元数据，不创建对象引用。

## 17. 测试策略

### 17.1 单元测试

覆盖：

- SHA-256 与对象路径生成。
- 相同内容只生成一个对象。
- 不同内容生成不同对象。
- 并发写入相同内容的幂等性。
- 用户逻辑用量按 SHA-256 去重。
- 跨用户分别计费。
- 内嵌图片不计配额。
- `0` 不限制，`1–99` 拒绝，`100+` 接受，默认 2048。
- LRU 选择最久未访问对象。
- 同一用户淘汰某哈希时清空该用户全部普通附件引用。
- 其他用户或内嵌图片仍引用时不删除物理对象。
- 最后引用删除时删除对象。
- 文件删除失败不会破坏业务引用删除结果。
- 旧路径安全校验和符号链接防护。

### 17.2 路由测试

覆盖：

- 设置读取和保存用户隔离。
- 降低上限触发清理统计。
- 本地对象命中时更新访问时间。
- 本地对象缺失时在线重新下载。
- 离线且无缓存时返回现有离线错误。
- 用户不能访问其他用户附件对象。

### 17.3 同步测试

覆盖：

- 历史同步不写普通附件文件。
- 历史同步仍缓存内嵌图片。
- 同步详情携带普通附件二进制时也不自动落盘。
- 正文 CID 替换保持可用。

### 17.4 迁移测试

使用独立临时目录和测试数据库验证：

- 普通附件旧文件被删除但元数据保留。
- 重复内嵌图片合并为一个对象。
- 迁移中断后重跑不重复删除、不丢引用。
- 无引用孤立文件安全删除。
- `/data/flymail/backup`、上传目录和配置目录不受影响。

### 17.5 Docker 验证

构建并启动临时容器，至少验证：

- 容器健康，版本正确。
- MySQL 8.0 和 `/data/mysql/` 正常。
- `/data/flymail/files/objects/sha256` 创建正常。
- 相同内容跨邮件、跨用户只占一份物理文件。
- 用户配额分别计算。
- 重启后对象、引用和设置保持。
- 降低容量后 LRU 清理生效。
- 日志无密码、令牌或完整数据库连接地址。
- MySQL 二进制日志仍关闭。

## 18. 发布与生产迁移

发布步骤：

1. 完成代码和自动化测试。
2. 构建新版本镜像。
3. 使用独立临时数据目录完成迁移和重启验证。
4. 记录生产迁移前附件目录大小、文件数和数据库引用数。
5. 安全停止当前生产容器。
6. 保留 `/Docker/flymail/data`，使用新镜像重建容器。
7. 等待健康检查通过和后台迁移完成。
8. 验证邮件正文、内嵌图片、普通附件按需下载、用户设置和配额。
9. 对比迁移前后邮件数、附件元数据数和磁盘占用。
10. 确认无异常后删除仅用于回滚的旧容器；默认不上传 Docker Hub。

生产迁移会删除现有普通附件本地缓存文件。这些文件仍存在于远端邮箱中，但离线账号在重新连接前无法重新下载未缓存附件。该行为属于已批准的空间优化范围，实施时仍需在最终部署前展示迁移统计并确认不会触及邮件正文、内嵌图片、远端邮件或备份目录。

## 19. 文档更新

## 20. 已确认决策

- 采用全局内容寻址存储方案。
- 每用户独立普通附件容量上限。
- 默认 2048 MB。
- `0` 表示不限制。
- 非零最小值为 100 MB。
- 正文和内嵌图片不计入容量上限。
- 普通附件和内嵌图片都做 SHA-256 内容去重。
- 全部相关引用删除后才删除唯一物理文件。
- 同一用户同哈希只计一次，不同用户分别计费。
- 超限时按每用户 LRU 淘汰。
- 调低上限后立即清理。
