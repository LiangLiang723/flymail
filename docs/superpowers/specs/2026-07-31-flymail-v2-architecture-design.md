# FlyMail V2 全面重构架构设计

日期：2026-07-31

状态：已完成逐段评审，等待最终书面确认

## 1. 背景与目标

FlyMail V2 将重写现有同步层、数据访问层和前端交互层，以获得稳定、快速、可恢复且适合长期维护的邮件系统。V2 不承担旧数据库和旧缓存兼容责任，正式切换时允许清空现有数据并从全新实例初始化。

V2 的目标部署规模：

- 最多约 50 个用户。
- 总计约 300 个邮箱账号。
- 单邮箱最多约 50 万封邮件。
- 总邮件记录约 2,000 万封。
- 桌面端和移动端功能尽量完整且同等优先。

V2 必须在正式切换前覆盖当前全部功能，包括登录与用户管理、邮箱账号管理、IMAP 收取、SMTP 发送、历史同步、实时增量同步、正文和附件缓存、全文与结构化搜索、定时发送、草稿、通知、备份恢复、同步管理、WebSocket 状态推送和管理员能力。

## 2. 已确认的架构决策

### 2.1 部署与基础设施

- 继续使用单容器部署。
- 容器内运行 MySQL 8、FastAPI API 进程、独立同步 Worker、前端静态资源和进程监督逻辑。
- API 与 Worker 使用独立数据库连接池。
- MySQL 是唯一可靠状态与任务协调核心。
- 不引入 Redis、RabbitMQ、Elasticsearch、对象存储服务或外部身份服务。
- 所有持久化数据继续位于 `/data`。

### 2.2 数据兼容边界

- 不迁移旧用户、邮箱账号、邮件缓存或附件缓存。
- 不保留旧数据库结构兼容层。
- 正式切换允许清空 `/Docker/flymail/data`，但实施切换前必须再次展示影响范围并获得明确确认。
- 开发和验证只能使用独立临时数据目录，不得写入生产数据目录。

### 2.3 产品与体验

- 前端允许全面重设计，只保留完整功能目标。
- 桌面端与移动端同等优先。
- 默认会话视图，一行代表一个会话。
- 同一用户的多个邮箱账号可以合并到同一会话。
- 会话级操作默认作用于整个会话，展开后可以单独操作某封邮件。
- 界面采用平衡型现代风格，支持舒适和紧凑两种密度。

### 2.4 安全与登录

- 保留本地用户名和密码登录。
- 首期不支持 OIDC 和双因素认证。
- 用户密码只保存强哈希。
- 邮箱密码、授权码和 OAuth 令牌使用实例密钥派生出的独立数据密钥进行认证加密。
- 邮件正文和附件不做应用层静态加密，以保留搜索、去重和性能能力。

## 3. 总体架构

```text
flymail container
├── mysqld
├── flymail-api
├── flymail-worker
├── frontend static assets
└── process supervisor / entrypoint
```

### 3.1 API 进程职责

API 只负责短请求和本地事务：

- 登录、会话和用户管理。
- 邮件列表、会话详情、正文读取和搜索。
- 草稿、发送、移动、标签、已读、星标和删除命令接收。
- 附件上传、下载鉴权和对象流式读取。
- 用户设置、管理员设置、备份恢复命令。
- WebSocket 实时事件连接。
- 原子写入业务状态、`mail_operations` 和 `outbox_events`。

API 不直接执行长时间 IMAP、SMTP、历史同步、正文补全、索引重建或垃圾回收。

### 3.2 Worker 进程职责

Worker 负责：

- IMAP IDLE 监听。
- 自适应周期校正。
- 初次和历史邮件同步。
- 摘要、正文、内嵌图片和原始源码获取。
- 离线操作提交和冲突处理。
- 即时发送、定时发送和 SMTP 结果校验。
- 正文全文索引生成与清理。
- 用户缓存配额、LRU 淘汰和孤立对象回收。
- 备份和恢复的后台阶段。

Worker 重启后必须从 MySQL 恢复任务，任何可靠任务都不能只存在于内存。

### 3.3 模块边界

```text
backend/
├── api/                  HTTP、WebSocket、认证与序列化
├── application/          用例、事务边界和命令编排
├── domain/               邮件、会话、操作、冲突和任务规则
├── repositories/         MySQL 数据访问
├── providers/
│   ├── core/             通用 IMAP、SMTP、MIME 与能力模型
│   └── plugins/          Gmail、Outlook、QQ、网易、iCloud、新浪、通用邮箱
├── workers/              调度、消费者和任务处理器
├── object_store/         内容寻址对象存储
├── search/               查询编译、全文索引与建议
├── security/             凭证加密、密码、会话和审计
└── observability/        指标、计时和安全日志
```

Repository 不访问网络或文件系统，不推送实时事件，也不隐式提交事务。Application Service 负责事务边界，Worker Handler 负责协议执行。

## 4. API 与 Worker 的可靠协作

采用 MySQL 任务表和事务型 Outbox。

用户操作在同一数据库事务中完成：

1. 校验用户与资源归属。
2. 更新本地投影状态。
3. 创建 `mail_operations`。
4. 创建 `outbox_events`。
5. 提交事务。

Worker 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取任务，并通过租约、心跳和尝试记录实现崩溃恢复。

任务结果分为：

- 成功。
- 可重试失败。
- 永久失败。
- 结果不确定。
- 需要用户处理的冲突。

任务必须拥有稳定幂等键。发送、移动和删除的重试不得造成重复发送、重复移动或误删。

## 5. 核心数据模型

### 5.1 身份与账号

- `users`：本地用户、角色、状态和密码哈希。
- `mail_accounts`：真实邮箱账号，归属于唯一用户。
- `mail_identities`：显示名称、From 别名、Reply-To、签名和默认身份。
- `provider_credentials`：加密凭证、算法版本和密钥版本。

同一账号可配置多个经过服务商允许的发件身份。回复单封邮件时默认使用收到该邮件的账号和匹配身份；回复跨账号会话时默认使用最新来信对应账号，并允许用户切换。

### 5.2 邮件与远端实例

- `messages`：用户范围内的逻辑邮件实体、标准化头部、摘要和线程关系。
- `message_headers`：完整规范化头部和线程构建字段。
- `message_remote_instances`：每个账号中的远端实例、稳定服务商 ID、UIDVALIDITY、UID、flags 和远端版本。
- `message_bodies`：正文缓存状态、对象引用和索引状态。
- `message_attachments`：附件元数据、真实 IMAP part specifier 和对象引用。

普通 IMAP 远端唯一键至少包含：

```text
account_id + mailbox_id + uidvalidity + remote_uid
```

跨账号或多标签场景可以共享内容对象，但必须保留独立远端实例和操作状态。

### 5.3 文件夹与标签

- `mailboxes` 同时表达普通 IMAP 文件夹和 Gmail 标签。
- `message_memberships` 保存远端实例与文件夹或标签的多对多关系。
- `mailboxes` 同时保存原生路径与统一语义键。

统一语义键包括：

- `inbox`
- `sent`
- `drafts`
- `trash`
- `junk`
- `archive`
- `all_mail`
- `important`
- `custom`

Gmail 保留原生多标签能力；归档通过移除 Inbox 标签实现，不复制邮件正文。

### 5.4 会话

- `threads` 保存稳定会话 ID。
- `thread_messages` 保存邮件节点及顺序。
- `thread_projections` 保存列表所需的最新主题、时间、参与者摘要、邮件数、未读数、星标、附件、账号数量和待同步状态。

线程优先依据 `Message-ID`、`In-Reply-To` 和 `References` 构建。标题只在头部缺失时，结合参与者和时间窗口进行保守降级，不能仅因 `Re:` 或相似主题合并。

## 6. 本地优先操作与冲突

浏览器必须能连接 FlyMail 服务，但第三方邮箱离线时仍可使用本地缓存和本地操作。浏览器不使用 IndexedDB 保存邮件数据库或离线队列。

支持本地优先：

- 已读和未读。
- 星标。
- 移动、归档和标签。
- 两阶段删除。
- 草稿。
- 即时发送和定时发送。

冲突规则：

- 已读和星标按字段独立合并。
- 移动、归档和标签基于操作创建时观察到的远端版本重新计算目标。
- 第一次删除移动到垃圾箱；垃圾箱中再次删除才永久删除，并要求二次确认。
- 草稿冲突保留本地和远端两个版本，不静默覆盖。
- 发送使用稳定 `operation_id` 和 `Message-ID`；SMTP 结果不确定时先校验已发送箱，再决定是否重试。
- 远端邮件已不存在时，相关操作终结，不无限重试。

前端明确显示“等待同步、正在同步、已同步、失败、冲突”。

## 7. 同步系统

### 7.1 IDLE 与周期校正

采用 IMAP IDLE + 自适应周期校正：

- 支持 IDLE 的账号保持一条监听连接。
- IDLE 只创建轻量增量任务，不在监听连接中执行正文下载或大量数据库写入。
- 活跃账号约每 5 分钟校正。
- 普通账号约每 15 分钟校正。
- 长期无变化账号逐步放宽到约 30 分钟。
- 网络恢复、用户打开账号、IDLE 重连或操作积压时立即校正。
- 不支持 IDLE 或连接不稳定时自动降级轮询。
- 连续失败采用指数退避和随机抖动。

### 7.2 任务优先级

| 优先级 | 任务类型 |
|---|---|
| P0 | 用户打开正文、下载附件、立即发送、手动重试 |
| P1 | 离线操作、新邮件摘要、当前页面刷新 |
| P2 | 最近正文、内嵌图片、全文索引 |
| P3 | 周期状态校正 |
| P4 | 历史正文、维护、垃圾回收 |

调度采用加权公平策略，慢账号不能阻塞其他账号，低优先级任务也不能永久饥饿。

### 7.3 并发边界

默认设计：

- 每账号最多 1 条 IDLE 连接。
- 每账号最多 2 条普通 IMAP 工作连接。
- 每账号最多 1 个状态修改任务。
- SMTP 使用独立限流。
- 每服务商插件声明最大连接数、命令间隔和推荐批次。
- 同一同步 IMAP 连接不并发执行多个命令。

### 7.4 初次和历史同步

阶段顺序：

1. 服务商能力、文件夹和标签发现。
2. 最近邮件摘要。
3. 其余历史摘要。
4. 最近正文和必要内嵌资源。
5. 历史正文低优先级补全。
6. flags、标签和远端状态校正。

每批处理有限数量后保存游标并让出执行权。摘要齐全后用户即可浏览目录，不等待全部正文下载。

长任务定期写心跳。单封大邮件耗时较长时，不得误判任务失效。同步进度必须分别展示摘要、正文、索引和状态校正，不得把“摘要完成”显示成“同步全部完成”。

## 8. 服务商插件与协议核心

### 8.1 通用核心

核心负责：

- TLS、认证、会话状态和命令串行化。
- CAPABILITY、IDLE、MOVE、UIDPLUS、CONDSTORE 和 QRESYNC 等能力处理。
- 文件夹发现与统一语义接口。
- MIME 和 BODYSTRUCTURE 解析。
- 精确正文和附件 part 获取。
- SMTP MIME 构建与投递。
- 超时、取消、错误分类和安全关闭。

### 8.2 插件职责

Gmail、Outlook、QQ、网易、iCloud、新浪和 Generic 插件只处理：

- 默认服务器与端口。
- 密码或 OAuth 认证差异。
- 特殊文件夹映射。
- Gmail 标签和稳定 ID。
- 连接、FETCH 和 SMTP 限流。
- 已发送副本策略。
- 服务商错误翻译和兼容修正。

插件不得直接操作数据库、对象存储或业务任务。

### 8.3 MIME 与附件

摘要阶段批量获取头部、flags、大小、日期和 BODYSTRUCTURE，不获取完整 MIME。

所有 MIME part 保存真实 IMAP part specifier，例如 `1.2` 或 `2.1`。禁止使用 `email.walk()` 序号代替远端 part 编号。

正文只获取选中的文本和 HTML part：

```text
BODY.PEEK[1.1]
BODY.PEEK[1.2]
```

普通附件仅在用户点击时获取对应 part，不使用 `BODY.PEEK[]` 拉取整封邮件。

内嵌图片只有在正文实际引用 CID、类型安全且大小合理时自动缓存。明显追踪像素和未引用资源不主动下载。

原始 RFC 822/MIME 源码仅在查看原文、导出 `.eml` 或解析异常时按需获取。

## 9. 分层缓存与对象存储

### 9.1 缓存策略

采用分层按需缓存：

- 所有邮件同步摘要、状态、线程字段、BODYSTRUCTURE 和附件元数据。
- 最近邮件、用户访问邮件和当前可见邮件优先缓存正文。
- 历史正文由后台低优先级逐步补齐。
- 普通附件点击后下载。
- 内嵌图片按正文引用自动缓存。

正文缓存状态使用明确枚举：

- `not_requested`
- `queued`
- `fetching`
- `ready`
- `evicted`
- `failed`
- `unavailable`

不再通过正文是否为空推断同步状态。

### 9.2 内容寻址对象存储

所有大内容存放于：

```text
/data/flymail/objects/<hash-prefix>/<sha256>
```

对象类型包括：

- HTML 正文。
- 纯文本正文。
- 内嵌图片。
- 普通附件。
- 按需缓存的 `.eml`。
- 草稿和待发送附件。

文件写入流程：临时文件写入、流式计算 SHA-256、大小和完整性校验、原子重命名、建立数据库引用。

不维护手工 `ref_count`。删除物理对象前实时确认所有引用均已消失。权限始终通过 MySQL 业务引用校验，不能凭哈希直接读取文件。

### 9.3 继承现有附件缓存标准

V2 继承 2026-07-30 附件缓存设计中已经验证的原则：

- 普通附件按需缓存。
- 内嵌图片自动缓存但不计入普通附件配额。
- SHA-256 全局物理去重。
- 每用户逻辑配额按其引用去重计算。
- LRU 淘汰只解除当前用户引用。
- 最后一个真实引用删除后才回收物理文件。
- 数据库引用、对象文件和垃圾回收具备崩溃恢复能力。

由于 V2 从全新数据开始，不保留旧路径迁移与旧缓存兼容逻辑。

### 9.4 正文配额

- 每用户可在设置中配置正文缓存容量。
- 默认值为 5 GB。
- `0` 表示不限制。
- 正文配额与普通附件配额分别统计。
- 最近访问、最近收到、星标和用户手动锁定的邮件优先保留。
- 草稿、待发送邮件和本地独有内容永不参与自动淘汰。
- 正文对象被淘汰时，对应完整正文 FULLTEXT 索引一并删除。
- 主题、地址、日期、标签等结构化搜索字段永久保留。
- 原始 `.eml` 纳入正文配额和 LRU。

## 10. 数据访问层与搜索

### 10.1 读写分离

代码层采用命令与查询分离：

- 写路径由 Application Service 管理事务、领域规则和 Outbox。
- 读路径由 Query Service 返回面向页面的轻量 DTO。
- 读取接口不复用具有同步副作用的服务。

Repository 按领域拆分，禁止再次形成单个超大数据库文件。

### 10.2 查询规则

- 所有用户数据查询显式限定 `user_uid`。
- 所有大列表采用稳定复合游标，不使用深度 OFFSET。
- 列表查询不连接正文对象或大文本字段。
- 同步摘要采用批量查找、批量 upsert 和有限事务。
- Repository 不隐式 `commit`，也不在逐封循环中提交。

核心游标示例：

```text
(latest_message_at, thread_id)
```

### 10.3 搜索

提供高级组合搜索：

- 主题、参与者和已缓存正文关键词。
- 发件人、收件人和抄送人。
- 日期和大小范围。
- 账号、文件夹和原生标签。
- 已读、星标和附件条件。
- 最近搜索和保存搜索。

MySQL FULLTEXT 只索引当前已缓存的规范化纯文本正文。原始 HTML 不进入搜索路径。正文淘汰后完整正文索引删除，但结构化字段仍可搜索。

搜索：

- 强制限定当前用户。
- 使用参数化 SQL 和受控字段映射。
- 默认按会话聚合。
- 标记具体匹配邮件和匹配字段。
- 不等待 IMAP，也不触发全账号远端搜索。
- 明确提示“正文搜索仅覆盖已缓存正文”。

## 11. 前端架构与交互

### 11.1 技术与目录

继续使用 Vue 3 + TypeScript，但按功能拆分：

```text
frontend/src/
├── app/
├── layouts/
├── features/
├── entities/
├── shared/
└── styles/
```

每个功能模块拥有页面、组件、API、状态、类型和测试。避免把列表、详情、搜索和同步状态集中在大型 Vue 文件中。

### 11.2 响应式布局

桌面端默认三栏：全局导航、会话列表、会话详情。

平板端使用两栏和可收起导航。

移动端使用文件夹、列表、详情和写信的页面推进模型，并通过抽屉和底部操作栏保留完整功能。

### 11.3 启动和请求缓存

登录后使用单一 `/api/bootstrap` 请求加载首屏必要状态，不重复请求当前用户。通知详情、设置和非首屏模块延迟加载。

服务器业务状态由统一查询缓存管理：

- 相同请求去重。
- 明确缓存键。
- 后台刷新和精确失效。
- 页面切换取消旧请求。
- 实时事件只更新受影响的会话。

浏览器不持久化邮件正文、附件、凭证或离线操作。

### 11.4 会话详情与写信

会话详情先返回结构、时间线和缓存状态，再按需读取正文。未缓存正文复用已有 P0 任务，不重复入队，也不无限显示加载动画。

写信支持多发件身份、富文本与纯文本、签名、附件、回复引用、草稿自动保存、定时发送和发送前撤销。

草稿使用服务器版本号；发生冲突时保留两个版本。

### 11.5 正文安全与可访问性

邮件 HTML 后端净化、前端二次净化并隔离渲染。默认阻止远程追踪图片，链接展示真实目标域名，邮件 CSS 不得污染应用界面。

必须支持：

- 深色和浅色主题。
- 邮件正文对比度修正。
- 完整键盘导航和快捷键。
- 屏幕阅读器标签和动态状态播报。
- 清晰焦点样式。
- `prefers-reduced-motion`。
- 合理的移动端触控目标。

## 12. 可靠发送

即时发送和定时发送使用同一套本地可靠队列：

1. API 原子保存正文、附件引用和发送任务。
2. API 立即返回任务 ID，不等待 SMTP。
3. Worker 构建标准 MIME 并投递。
4. 服务商插件决定是否需要 APPEND 已发送副本。
5. 任务状态为排队、发送中、已发送、失败或需要校验。

固定 `Message-ID` 和幂等键防止重复发送。SMTP DATA 后连接断开等不确定情况进入 `verification_required`，检查已发送箱后再决定处理。

Bcc 只用于 SMTP envelope，不出现在公开邮件头。

## 13. 安全、审计和备份

### 13.1 用户隔离

隔离由 API、Application Service、Repository、对象下载、WebSocket 和 Worker 多层保证。任何邮件、账号、附件、任务和会话查询都必须验证用户归属。

管理员默认不能查看用户邮件正文、附件、草稿或完整搜索历史。

### 13.2 日志与审计

审计记录登录、密码修改、用户管理、账号管理、重新授权、永久删除、备份恢复、密钥轮换、冲突人工处理和管理员高风险操作。

运行日志使用结构化字段，但不得包含密码、令牌、正文、附件内容、完整数据库 URL 或完整收件人列表。数据库 URL 密码统一显示为 `***`。

### 13.3 备份范围

备份配置和业务数据，包含：

- 用户、角色和设置。
- 邮箱账号、发件身份和重新加密后的凭证。
- 邮件摘要、头部、文件夹、标签和会话关系。
- 草稿正文与附件。
- 待发送和定时发送内容。
- 离线操作、同步游标和保存搜索。

不包含：

- 可重新获取的远端正文缓存。
- 内嵌图片和普通附件缓存。
- 按需缓存的 `.eml`。
- 可重新生成的正文全文索引。
- 临时文件和运行日志。

备份使用管理员独立密码重新加密凭证，可跨机器恢复，不依赖旧实例的 `FLYMAIL_SESSION_SECRET`。恢复先写入临时数据库和临时对象目录，通过完整校验后原子切换；失败不得破坏现有系统。

备份快照中的未完成发送、定时发送和离线远端操作在恢复后统一进入 `review_required` 或暂停状态。系统必须先依据稳定 `operation_id`、`Message-ID` 和远端当前状态重新校验，不能因为恢复了旧快照而自动发送或执行可能已经完成的过期操作。

## 14. 可观测性与健康检查

API 指标包括请求总耗时、数据库等待、查询、对象读取、解压、序列化、结果数和响应字节。核心接口提供 `Server-Timing`。

Worker 指标包括队列等待、执行耗时、重试、租约超时、IMAP 连接、IDLE 在线率、FETCH 字节、MIME 解析、SMTP、限流、缓存命中和配额淘汰。

基础 `/api/health` 只反映 API、MySQL 和 Worker 是否可处理请求。单个第三方邮箱故障不能导致容器健康检查失败。管理员详细诊断另外鉴权提供。

## 15. 测试体系

测试分层：

1. 领域单元测试。
2. 使用真实 MySQL 8 的 Repository 集成测试。
3. IMAP、SMTP 和 Provider 合同测试。
4. Application Service 和 API 测试。
5. 前端组件、桌面和移动流程测试。
6. 单容器集成测试。
7. 容量、性能和故障注入测试。
8. 使用测试邮箱的真实验收。

必须覆盖：

- Outbox 与业务事务原子性。
- 多消费者领取不重复。
- 游标分页不重不漏。
- 用户隔离。
- UIDVALIDITY 变化。
- MIME 异常和真实 part 获取。
- 普通附件不提前下载。
- SMTP 结果不确定和重复发送防护。
- Worker、API 和 MySQL 中断恢复。
- 磁盘满、对象缺失和孤立对象。
- 备份错误密码、损坏文件和恢复回滚。
- 桌面、移动、深浅主题和无障碍。

## 16. 性能验收门槛

目标容量数据集为 50 用户、300 账号和 2,000 万封摘要记录。

### API

| 指标 | 门槛 |
|---|---:|
| Bootstrap P95 | ≤ 300 ms |
| 会话列表 P95 | ≤ 150 ms |
| 会话结构 P95 | ≤ 150 ms |
| 已缓存正文首字节 P95 | ≤ 200 ms |
| 结构化搜索 P95 | ≤ 300 ms |
| 已缓存正文全文搜索 P95 | ≤ 500 ms |
| 本地操作提交 P95 | ≤ 200 ms |
| API 数据库连接等待 P95 | ≤ 50 ms |

### Worker

| 指标 | 门槛 |
|---|---:|
| P0 任务排队 P95 | ≤ 500 ms |
| IDLE 新邮件发现到列表可见 | ≤ 5 秒 |
| 网络恢复后操作开始执行 | ≤ 5 秒 |
| Worker 重启任务恢复 | ≤ 30 秒 |
| 重复发送 | 0 |
| 普通附件提前下载 | 0 字节 |
| 慢账号阻塞其他账号 | 不允许 |

### 前端

| 指标 | 门槛 |
|---|---:|
| 初始 JS gzip | ≤ 180 KB |
| 应用壳出现 | ≤ 300 ms |
| 登录后可交互 | ≤ 1.5 秒 |
| 列表操作反馈 | ≤ 100 ms |
| 已缓存正文打开反馈 | ≤ 100 ms |

## 17. 单容器生命周期

启动顺序：

1. 校验环境变量和秘密长度。
2. 创建 `/data` 目录。
3. 初始化或启动 MySQL。
4. 执行数据库迁移。
5. 验证对象存储可写性。
6. 启动 Worker。
7. 启动 API。
8. 通过健康检查。

任一关键进程退出时，容器停止接受新写请求并安全关闭其他进程，由容器平台重启。入口脚本不无限静默重启崩溃进程。

终止时 API 停止新写入，Worker 停止领取任务并释放租约，IDLE 安全退出，数据库连接池关闭，最后安全关闭 MySQL。

## 18. 开发拆分与发布策略

V2 作为一次完整产品切换发布，但实现必须拆成可独立验证的内部子项目：

1. V2 基础骨架、数据库迁移框架、对象存储和安全基础。
2. 新数据模型、Repository、Outbox、任务租约和投影。
3. 通用 IMAP/SMTP 核心和 Provider 插件合同。
4. 摘要同步、IDLE、周期校正和历史游标。
5. MIME 分段正文、附件、内嵌图片和原始源码。
6. 离线操作、冲突、可靠发送和草稿。
7. 搜索、缓存配额、LRU 和维护任务。
8. 新前端桌面和移动体验。
9. 管理员、通知、备份恢复和审计。
10. 容量、故障、安全、真实邮箱和单容器验收。

每个子项目都必须有单独规格、实施计划和测试门槛。只有全部当前功能、性能和发布门槛通过后，才允许替换生产容器。

## 19. 正式切换与回滚

开发期间当前 `flymail` 容器保持运行，V2 使用独立临时容器和数据目录。

正式切换前必须：

- 完成所有自动化、容量、安全和真实邮箱验收。
- 构建最终本地镜像。
- 保存旧版完整数据目录快照。
- 明确展示将删除的目录、数据量、当前版本、新版本和回滚边界。
- 再次获得清空旧数据的明确确认。

V2 不兼容旧数据库。回滚旧版必须恢复旧版数据目录快照，不能让旧版读取 V2 数据库。V2 切换后产生的新草稿和操作不能自动回灌旧版。

## 20. 非目标

V2 首次发布不包含：

- Redis 或外部消息队列。
- Elasticsearch、OpenSearch 或其他独立搜索服务。
- OIDC 单点登录。
- TOTP 双因素认证。
- 浏览器 IndexedDB 邮件离线数据库。
- 多节点或多容器横向扩容。
- 旧数据库和旧缓存迁移。
- 管理员默认浏览用户邮件内容。
- 任意复杂搜索语法和自由 SQL。

## 21. 最终成功标准

V2 只有在以下条件全部满足时才算完成：

- 当前功能全部重新实现并通过回归。
- 数据与用户隔离具备自动化证明。
- 普通附件同步阶段不下载二进制。
- 正文、附件和 `.eml` 使用精确 MIME part 或明确按需源码获取。
- 用户操作本地即时生效，远端任务可恢复且幂等。
- SMTP 重试不会重复发送。
- 慢账号不会阻塞其他账号。
- 2,000 万封目标数据集达到性能门槛。
- 桌面和移动端核心功能、无障碍和主题全部通过。
- 备份恢复可跨实例运行，错误恢复不会破坏原数据。
- 临时单容器健康、重启、持久化、安全关闭和秘密扫描全部通过。
- README、环境变量、部署、备份和故障处理文档完整。
