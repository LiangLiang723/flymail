# 邮箱全局排序设计

## 目标

在“同步管理”页面为每个邮箱卡片提供“置顶 / 上移 / 下移”操作。用户调整后的顺序作为该用户的全局邮箱顺序，决定邮件管理、写信默认发件邮箱、移动端侧栏、同步管理、邮件备份和聚合收件箱相关账号列表的排列；排在第一位的邮箱作为没有既有选择时的默认邮箱。

## 交互设计

排序入口只放在同步管理页每张邮箱卡片现有的“···”菜单中：

- `置顶`：把当前邮箱移动到第一位。
- `上移`：与前一个邮箱交换位置。
- `下移`：与后一个邮箱交换位置。
- 第一项禁用“置顶”和“上移”。
- 最后一项禁用“下移”。
- 点击后立即保存，不进入独立排序模式，也不增加拖拽交互。

排序操作成功后，当前同步管理列表立即更新；其他页面下一次读取账号状态时使用同一顺序。当前已选择的邮箱不因排序自动切换，只有没有有效选择时才使用新的第一项。

## 数据模型与后端

复用现有 `accounts.sort_order` 字段，不新增数据库表，不迁移邮件或附件数据。

账号查询统一按以下顺序返回：

1. `sort_order ASC`
2. `created_at ASC`
3. `id ASC`

为兼容历史数据中全部为 `0` 的顺序，批量排序接口会为当前用户提交的完整账号 ID 列表依次写入 `0..n-1`。新建账号使用当前用户最大 `sort_order + 1`，默认排在最后。

新增当前用户专用批量排序接口：

```text
PUT /api/accounts/order
{"account_ids": ["id-1", "id-2", "id-3"]}
```

后端必须验证：

- 列表不包含重复 ID。
- 列表数量与当前用户账号数量一致。
- 提交集合与当前用户账号 ID 集合完全相同。
- 不允许通过该接口修改其他用户账号。

验证失败不写入任何排序值；验证通过后在同一数据库事务内更新全部账号顺序。

## 前端状态流

`mailStore` 增加统一的账号顺序保存动作：

1. 复制原始顺序。
2. 在内存中乐观调整 `accounts`。
3. 同步更新 `sessionStorage`。
4. 调用批量排序接口。
5. 成功后保留新顺序。
6. 失败时恢复原顺序与会话缓存，并显示错误提示。

同步管理页加载任务时，后端返回顺序必须与账号全局顺序一致；卡片菜单调用 `mailStore` 的置顶、上移或下移动作。排序期间禁用重复排序操作，避免并发请求覆盖。

邮件备份等不直接复用 `mailStore.accounts` 的接口也必须依赖后端 `get_accounts()` 的统一排序，因此不需要各页面重复实现排序逻辑。

## 用户隔离与安全

- 排序仅修改当前登录用户拥有的账号。
- 请求体不能包含缺失、额外或重复账号 ID。
- 不记录邮箱密码、授权码、令牌或数据库连接信息。
- 不删除或移动邮件、附件、用户和 `/Docker/flymail/data`。

## 错误处理

- 排序接口返回验证错误时，前端恢复原顺序并显示“保存邮箱顺序失败”。
- 网络错误或服务异常同样回滚。
- 同步管理任务刷新与排序请求相遇时，以排序操作中的账号顺序为准；排序完成后重新读取同步任务，确保卡片数据与最新顺序一致。

## 测试与验收

后端测试覆盖：

- `get_accounts()` 按 `sort_order` 返回。
- 新邮箱默认排在最后。
- 批量排序成功并持久化。
- 缺失、额外、重复及其他用户账号 ID 被拒绝。
- 验证失败时原顺序不变。

前端测试覆盖：

- 置顶、上移、下移生成正确账号顺序。
- 第一项与最后一项操作正确禁用。
- 保存成功更新内存与会话缓存。
- 保存失败恢复原顺序。
- 同步管理菜单包含排序操作，并通过统一状态仓库保存。

部署验收：

- 后端和前端全量测试通过。
- 前端生产构建通过。
- Shell、Docker Compose 和 Git diff 检查通过。
- 构建新版本镜像并使用独立临时数据目录验证健康、MySQL 8.0、持久化、日志脱敏、镜像元数据和安全停止。
- 生产容器替换后继续挂载 `/Docker/flymail/data:/data`。
- 使用真实登录会话调整邮箱顺序，刷新接口与重启容器后顺序保持。
